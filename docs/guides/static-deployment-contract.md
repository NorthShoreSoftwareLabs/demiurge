# Static Deployment Contract

A Demiurge static build produces a file tree and a manifest. Any platform that
serves those files correctly and applies the manifest rules gets a working
deployment. This document names the rules a static host must satisfy, separate
from the settings a specific platform chooses. Read the
[data and caching guide](./data-and-caching.md) first for the build-side of
each rule. [Vercel static output](./data-and-caching.md#vercel-static-output)
is one conforming implementation of this contract.

A rule below is a framework requirement when the build enforces or depends on
it. A setting is a provider choice when the platform decides the value and the
application only reads it.

## Manifest format and route rewriting

**Framework requirement.** `generateStaticOutput()` writes
`demiurge-static-manifest.json` to the output directory. The manifest declares
the HTTP status, path, response headers, and security policy for every
generated document. Every file hash, locale, and parameterized route that the
build produces shows up as an entry in the manifest. File header rules cover the
remaining static files generated by the build.

**Provider setting.** The host must read the manifest and apply its rules. The
host mounts the output directory at the site root. For each entry with a 200
status, the host serves the file at the entry's pathname with the declared
headers. For each entry with a 404 status, the host rewrites requests matching
that pathname to serve the file with status 404 and the declared headers.

For pathnames not matched by any manifest entry, the host must apply the
framework file header rules to serve the file, if it exists. The rules in the
manifest always take precedence. A pathnames matched by no entry and no file
rule gets a natural 404 and default headers.

## Security headers and content policy

**Framework requirement.** The generated manifest entries include a computed
security policy. The build collects the root policy, every route policy, and all
declared security patterns. It hashes in-document structured data. The manifest
entry declares the final combined policy and all other security headers
(`x-content-type-options`, `x-frame-options`, `cross-origin-embedder-policy`,
and others) as computed for that request.

**Provider setting.** The host applies the declared headers from the manifest.
The security headers never vary by request, because the manifest is static.
They are the same for every user and moment, written at build time. Other
security headers (`x-content-type-options`, `x-frame-options`,
`cross-origin-embedder-policy`) are computed and applied the same way.

## Immutable and revalidated file caching

**Framework requirement.** The build hashes the content of browser assets and
produces filenames like `app-abcdef123456.js`. The manifest rules mark these
files as immutable: `cache-control: public, max-age=31536000, immutable`. Files
that are not content-addressed, like `index.html`, must revalidate: `max-age=0,
must-revalidate`.

The manifest declares a `fileHeaderRules` array that covers Vite assets and
`public/` files not matched by specific route entries. Each rule gives a
pattern, typically a file extension or basename pattern, and a set of headers.
Patterns are matched as ECMAScript regular expressions against the file
basename. Matching stops at the first pattern that matches.

**Provider setting.** Whether a specific platform enforces immutable semantics,
supports entity tags, or sends `If-None-Match` requests is a platform property.
Treat the declared cache control headers as the authoritative policy. Serve
immutable files with long cache lifetimes. Serve revalidated files with a cache
lifetime of zero and a revalidation mechanism (entity tag or last-modified
date).

## Base paths and asset URL handling

**Framework requirement.** The build assumes the site is mounted at the root
(`/`). The generated manifest and static files reflect that assumption. An
application that declares a non-root base path in its route configuration
creates assets with relative URLs inside the shell document. The framework does
not rewrite asset paths at build time.

**Provider setting.** A static host that serves under a non-root path like
`/blog/` must configure that path in the framework route configuration and
rebuild. A CDN or reverse proxy that creates a virtual non-root mount does not
work. In-document asset URLs would break. The application must know its base
path at build time.

## Unsupported runtime behavior

**Framework requirement.** A static build includes no server code. Request
handlers are rendered to static documents or to static route manifests. No
handler code runs at request time.

**Provider setting.** The host must not promise capabilities that require
runtime code. Forwarding request bodies, checking authorization tokens,
computing responses, or calling out to services are not available. The
deployment is a file tree and a rule set. A request that needs computation
cannot be satisfied by static hosting alone.

## Conforming deployments

Services like Netlify, GitHub Pages, Cloudflare Pages, Amazon S3, and Firebase
Hosting satisfy every rule above when they support the following:

- Reading and applying the static manifest, either by parsing it or by
  accepting it as input to a build configuration.
- Serving files with custom headers per-path.
- Rewriting requests to fallback files (for 404 entries in the manifest).
- Distinguishing immutable from revalidated cache control in their CDN layer.

The simplest conforming deployment is a reverse proxy in front of a static file
server, with routing rules sourced from the manifest.
