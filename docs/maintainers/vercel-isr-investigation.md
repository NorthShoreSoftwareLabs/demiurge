# Vercel ISR investigation

This record defines the technical evidence boundary for [issue #481](https://github.com/NorthShoreSoftwareLabs/demiurge/issues/481).
[RFC 0230](../../rfcs/0230-cdn-cache-invalidation.md) contains the proposed representation cache contract.
Public API acceptance requires the provider proof specified in that RFC.

## Baseline and evidence boundary

Baseline commit: `502eea236d3532f707aa1e286eb385cb934e2d95`.
At this baseline, the Vercel adapter disables runtime response caching with `no-store`.
Its build produces no ISR targets or prerender configuration.
This investigation adds no public response cache API.

Provider documentation describes platform behavior.
A local provider model tests framework mechanisms under explicit assumptions.
Neither source proves the deployed behavior of Demiurge artifacts.
The live record below tests disposable provider artifacts.
Its results reject the tested representation configuration.

## Local generation candidate

A generation receives a new disposable data store.
That store has no shared entries when generation starts.
Request-local deduplication remains available inside the generation.
Generation writes affect only its disposable store.
It performs no writes to the ordinary shared data store.

This candidate avoids reading an old shared entry during regeneration.
It also avoids replacing shared entries after a concurrent invalidation.
External data caches remain under application control.
An application must provide fresh external data when generation requires it.

Document and navigation use separate representation identities.
Independent generations can read different data versions.
A shared provider group gives no local snapshot guarantee.
Concurrent probes must measure the resulting consistency limits.
No result can claim atomic replacement without provider evidence for both representations.

## Disposable provider artifact

Use a dedicated verification project with no production domains or private application data.
Build the fixture through published package exports.
Keep its server files outside the public asset directory.

The fixture requires these artifacts:

- Build Output API version 3 routing configuration.
- Separate document and navigation function targets.
- One public versioned route and one private control route.
- Explicit positive `expiration` values for public targets.
- One shared group for related representation targets.
- An explicit query allowlist for each target.
- A random server-only `bypassToken` for authenticated provider requests.
- An uncached control operation for version changes and controlled generation failures.

Reject unsupported methods before selecting an ISR target.
Control generation inputs before application code reads them.
Reject direct access that could bypass representation routing or private response exclusions.
Keep the control operation outside every shared cache rule.
Use deterministic counters to distinguish generation from cache hits.

## Live verification protocol

Further live probes require authorization and access to the dedicated project.
Record the artifact commit, deployment identifier, runtime, region, expiration, group, and routing configuration.
Record each request method, path, query, safe headers, response status, cache status, version, and invocation counter.
Preserve response security headers in the evidence.
Redact credentials before storing request evidence.

First establish a cold public response.
Repeat the request until the evidence identifies a cache hit.
Compare the hit with its generation response.
Run each matrix row against both a cold entry and a populated entry.
After each attempted private population, request the same public key from a separate client.

### Representation and security matrix

| Input | Required observation |
| --- | --- |
| Document and navigation requests | Each response keeps its own media type, body, headers, and cache identity. |
| Spoofed `x-demiurge-navigation` | An untrusted value cannot select or populate another representation. |
| Allowed query value changes | Each declared variant receives the intended identity and generation input. |
| Unknown and repeated query parameters | Filtering prevents undeclared inputs from changing a stored public response. |
| Cookie and authorization credentials | Private inputs cannot enter a stored public response. |
| Valid and invalid bypass cookies | Private bypass output cannot replace a public entry. |
| `Set-Cookie`, `private`, and `no-store` responses | Provider behavior preserves the required shared storage exclusions. |
| Declared public `Vary` headers | Every declared variant remains separate on cache hits. |
| `Vary: Cookie` and `Vary: *` | Shared storage remains disabled. |
| Mutation methods and private control paths | Requests reach uncached application handling. |
| Required per-request route behavior | Cache hits preserve that behavior through a verified boundary, or the route remains ineligible. |
| Security headers and nonce documents | Hits preserve required headers. Per-request nonce documents remain outside ISR storage. |
| Direct function paths and rewritten paths | Neither access path bypasses the intended request boundary. |

### Freshness and failure matrix

| Operation | Required observation |
| --- | --- |
| Timed expiration after a data update | Regeneration reads fresh data under the selected generation rule. |
| Explicit path revalidation after a write | Both representations follow the same documented freshness rule. |
| Concurrent dynamic route refresh | Route keys remain separate and versions reveal ordering limits. |
| Concurrent document and navigation generation | Evidence identifies any mixed versions or independent snapshots. |
| Controlled regeneration failure | Evidence records stale serving, retry timing, and subsequent recovery. |
| Failed regeneration of one representation | Evidence identifies consistency with the related representation. |
| Repeated invalidation requests | Evidence records provider responses and resulting generations. |
| Lost invalidation acknowledgment | The client reports unknown acceptance without claiming that no work occurred. |
| Deployment replacement and rollback | Evidence identifies cache scope, retained versions, and old generation effects. |

For on-demand revalidation, send `GET` or `HEAD` with `x-prerender-revalidate` to the intended prerender path.
Distinguish provider acknowledgment from observed replacement of every required representation.
Do not infer global propagation from one region.
Report any unobserved region or representation explicitly.

## Credential and authority boundary

Configure an exact HTTPS deployment authority for invalidation.
Validate the destination before attaching the bypass token.
Reject user information, alternate authorities, and unsupported URL forms.
Disable redirects on authenticated provider requests.
Never derive the destination authority from request headers or caller-supplied absolute URLs.
Keep the token outside browser output, logs, telemetry, redirects, and client-visible errors.

A timeout can occur after provider acceptance.
Report that uncertainty without exposing the provider response body.
Applications own durable delivery when their product requires repeated invalidation attempts.
An accepted provider request does not establish durable delivery of later application requests.

## Acceptance limit

Local artifacts can establish packaging, input controls, operation order, and modeled failure handling.
Only authorized live probes can establish provider cache behavior, propagation, grouping, and rollback behavior.
If a required condition fails, revise RFC 0230 before public implementation.
